# ADR-0013: 冷启动建仓推荐 —— 复用组合管道，强制分批与成绩单

- 状态: 已接受
- 日期: 2026-08-31
- 相关: [09-portfolio-risk](../09-portfolio-risk.md) 第 8 节, [ADR-0009](0009-monitor-three-tier-funnel.md), [14-risk-register](../14-risk-register.md) R-21/R-24

## 背景

需求：为**还没有持仓的用户**根据全局判断给出建仓推荐。

现有设计假设用户已有组合，每日输出的是调仓建议（`target_weight` vs `prev_weight`）。空仓用户拿到这个没有意义——它是"从当前持仓出发调什么"，不是"从零开始买什么"。

## 决策

**五条：**

1. **不新建 Agent 或模型。** 复用 `PortfolioEngine` 的 ①-⑥ 步（它们本来就不参考现有持仓）。
2. **不复制现有持仓。** 必须重跑 ①-⑥ —— 持有理由 ≠ 买入理由。
3. **资金量是一等公民。** `top_n` 由资金量推导，新增可执行性排除规则。
4. **默认分批建仓**（4 批 × 5 交易日间隔）。
5. **输出强制包含对照组与 shadow 历史成绩。** 无成绩记录则不发布该功能。

放在 **P5**，不能更早。

## 理由

### 一、能力已存在，缺的是命名与暴露

回看构建流程：

```
①筛选 ②排序 ③初始权重 ④波动率调整 ⑤相关性去冗余 ⑥总仓位缩放  ← 不看现有持仓
                                                    ↓
                                          ⑦换手约束  ← 才引入 current
```

**①-⑥ 的输出本身就是"如果从零开始，我会持有什么"。**

所以不需要新 Agent、新信号、新模型。这与 [ADR-0009](0009-monitor-three-tier-funnel.md) 决定不新建 MonitorAgent 同源：管道已经算出来了，新建意味着新 prompt、新测试、新评估，且能力重复。

### 二、持有理由 ≠ 买入理由

**这是最容易图省事出错的地方。**

假设 shadow portfolio 持有某股，成本 10 元，现价 15 元。对已持仓者是"继续持有"，但不等于对新用户是"现在买入"：

| 混入持有决策的因素 | 对新建仓是否适用 |
|---|---|
| 换手成本（卖出要付费） | **不适用**（本来就没持有） |
| 印花税考虑 | **不适用** |
| "不想卖"的路径惯性 | **不适用** |
| 当前价位的剩余空间 | ★ `min_score` 不覆盖 |

所以实现上明确禁止直接读取 `shadow_cn` 的持仓，有测试保障：

```python
def test_cold_start_not_copy_of_current_holdings(): ...
```

### 三、A 股整手让小资金无法执行标准配置

`top_n: 15` 不能是常量。A 股买入最小 100 股（科创板 200 股，**需核实**）。

反算单票可买最高股价：`P_max = capital × max_single_weight / min_lot_buy`

| 资金 | 单票上限 10% | P_max | 可行持仓数 |
|---|---|---|---|
| 5 万 | 5,000 | 50 元/股 | 8-10 |
| 10 万 | 10,000 | 100 元/股 | 12-15 |
| 20 万 | 20,000 | 200 元/股 | 15-20 |

资金 5 万买一手 100 元的股票就是 20% 权重——**会被 RiskEngine 拒掉**。若不在组合层提前排除，用户会收到一份大部分标的无法执行的清单。

新增两项：

```python
EXCLUSION_RULES_COLD_START = EXCLUSION_RULES + [
    "last_price * min_lot_buy > capital * max_single_weight",
]

def derive_top_n(capital, candidates, cfg, market_cfg) -> int: ...
```

资金 < 3 万时建议持仓数 ≤5：**不是因为分散不好，而是再分散每票买不到一手，且佣金最低 5 元会吃掉收益**（单笔 3000 元时佣金占 0.17%，是标准费率数倍）。

**用户只投一部分时，用可投入资金重算，不按总额打折。** 账户 10 万只想投 3 万，就用 3 万算组合。若按 10 万算完再缩到 30%，某票 8% 权重（8000 元）会缩到 2400 元——**可能连一手都买不起**。而整手可行性恰恰是在 `derive_top_n` 用全额资金校验的，校验完打折等于校验作废。所以 `investable_capital` 是冷启动唯一的资金输入。

被排除的标的**必须在输出中展示**（`recommendation_excluded` 表）——否则用户不知道错过了什么，也不知道加资金的价值。

### 三之二、板块交易权限是比资金量更硬的约束

A 股科创板/北交所需 50 万 + 24 个月经验 + C4，创业板需 10 万 + 24 个月 + C4（已核实 2026-09-03）。这不是偏好，是"开不了权限就一股都下不了单"。

它与资金量约束是同一类问题（可执行性）的两个维度：

| 维度 | 约束 | 处理 |
|---|---|---|
| 资金量 | 买不起一手 | `EXCLUSION_RULES_COLD_START` |
| 板块权限 | 开不了权限 | `EXCLUSION_RULES` 的 `tradable_boards` |

**做成用户声明式配置，默认最保守（仅主板）。** 因为 A 股阶段无 API，系统无法自动探知用户开通了哪些板块。默认全开会推荐无法执行的标的，默认全关又过度保守。

一个关键分野：**研究分析保留全部板块，仅建仓推荐按 eligibility 过滤。** ChiefAgent 的市场判断需要覆盖科创板龙头（它们影响整个市场），但落到"给你的清单"时必须过滤。同一份分数，不同的过滤器。被过滤的标的按 `BOARD_NOT_ELIGIBLE` 展示，提示"开通后可解锁"——与展示"因资金量排除"同一意图：**排除必须可见。**

### 四、一次性建仓的时点风险不可忽略

调仓每天只动边际；**冷启动一次性决定全部仓位的成本基础**。若那天恰好是局部高点，之后很长时间都在解套。

更麻烦的是它污染归因：**无法区分"策略不行"和"建仓时点不好"。**

```yaml
cold_start:
  scale_in:
    enabled: true          # ★ 默认开启
    tranches: 4
    interval_days: 5
    first_tranche_ratio: 0.40
```

分批期间标的失效的处理（容易漏掉的分支）：

| 情况 | 动作 |
|---|---|
| 分数跌破 `min_score` | `abort_remaining` — 停止后续加仓，**不卖出已建仓部分** |
| 触发排除规则（ST/停牌） | `abort_remaining` |
| 涨停买不进 | `skip_this_tranche` — 顺延 |
| 组合回撤超阈值 | 全部 `abort_remaining`，重新走冷启动 |

**"不卖出已建仓部分"是刻意的**：卖出决策应走正常调仓流程和风控，不由建仓计划决定。否则会出现"建仓计划自带止损逻辑"这种职责混乱——与 [ADR-0007](0007-risk-not-agent.md)（风控判定归 RiskEngine）同源。

#### 分批的资金边界与 stance 追加

分批分的是**已决定投入的 `investable`**，两条不可越界的规则：

| 边界 | 规则 |
|---|---|
| 未投入资金（`investable` 之外） | **永不自动触碰**；追加须用户显式发起新推荐 |
| `investable` 内 stance 留出的现金 | 可随市场转好在 `investable` 上限内追加 |

第一条是信任底线——"我说投 3 万，系统不能偷偷把剩下 7 万也投了"。

**追加时机由系统判断，不让用户盯盘。** 系统每天重算 stance，若建仓期间 stance 上升（defensive→moderate），原本留的现金可投入，走 `increase_exposure`，通过 `REC_STANCE_UP` 推送建议。这与"盘后批处理主动推送"的系统定位一致，也零 LLM 成本。

**方向不对称是刻意的**：stance 转差 → `abort_remaining`（停止加仓）；stance 转好 → `increase_exposure`（可追加）。两个方向都响应市场，但都**不卖出已建仓部分**，且追加**永不越过 `investable`**。

### 五、这是最接近"荐股"的功能，必须自带成绩单

日报是研究；"给空仓用户的 12 只建仓清单"在观感上非常接近投资建议。这会显著加剧 R-24（误当赚钱工具，评级中概率/**致命**）。

**免责声明不够，需要设计上的约束**：

| 强制要求 | 作用 |
|---|---|
| 展示对照组（含随机选股 95 分位） | 让用户看到是否真的超出随机 |
| 展示 shadow 实际历史成绩 | 不是回测数字，是真实前向记录 |
| 展示过往推荐的结果分布（不只是好的） | 对抗选择性记忆 |
| 若随机选股分位超过本策略，**显著标注** | 诚实优先于好看 |

目标：让用户看到的不是一份清单，而是**一份带成绩记录的清单**。

**若做不到（如 shadow 数据不足），该功能应延后而非降低要求。**

### 六、推荐 ≠ 实际持仓

引入第三种持仓状态：

| 状态 | 载体 |
|---|---|
| 用户实际持有 | `manual_position` |
| 系统假设持有 | shadow portfolio |
| **已推荐未执行** | `recommendation`（新增） |

三个具体问题：

| 情况 | 处理 |
|---|---|
| 推荐 12 只，用户只买 3 只 | 记录执行率，**归因用 shadow 不用用户实际持仓** |
| 推荐后未买，股价涨了 | 记入 shadow，不记入用户 PnL |
| 监控需要 `avg_cost` / `entry_high` | 未执行的推荐无这些字段，触发器需降级 |

R-21（建议模式自欺）在这里会放大：用户会记住"推荐的那只涨了"，忘记"我没买"和"另外 11 只没涨"。

缓解是纯工程的（与 R-21 一致）：`recommendation` append-only 触发器，`v_recommendation_quality` 强制展示执行率与全部结果分布。

**归因必须用 shadow**：若用用户实际执行的部分做归因，"只买了后来涨的那几只"会让统计严重失真。

### 七、为什么放 P5

**冷启动决定全部仓位，调仓只影响边际。所以它需要更完整的风控，不是更少。**

| 前置能力 | 阶段 | 缺了会怎样 |
|---|---|---|
| 相关性去冗余 | P5 | 推荐 12 只同板块股票，看似分散实为一个赌注 |
| 波动率调整 | P5 | 高波动标的权重过高 |
| 总仓位管理 stance | P5 | 不知道该买七成还是三成 |
| 全部 hard 风控 | P5 | 可能违反行业集中度约束 |
| Shadow 历史成绩 | P4 | 无成绩可展示，无法对抗 R-24 |

A 股同概念板块内相关性极高，第一条不是理论风险。

另外 P1 MVP 的 Agent 明确"禁止给买卖建议"，冷启动推荐属于买卖建议。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 新建 `AllocationAgent` 专门做建仓推荐 | `PortfolioEngine` ①-⑥ 已经是答案；新建意味着重复能力 |
| 直接返回 shadow portfolio 当前持仓 | 持有理由 ≠ 买入理由；混入了换手成本与路径惯性 |
| `top_n` 固定 15 不考虑资金量 | 小资金买不起，清单大部分不可执行 |
| 按账户总额算组合再打折到投入金额 | 打折让某些标的达不到一手，破坏整手可行性；应用可投入资金重算 |
| 分批建仓期间自动动用未投入资金 | 违反用户投入意愿，严重信任问题；追加须用户显式发起 |
| stance 转好由用户盯盘判断是否追加 | 违背系统定位；系统每天算 stance，应主动推送 `REC_STANCE_UP` |
| 整手向上取整凑足目标权重 | 可能突破单票上限或总仓位上限 |
| 强行用剩余现金凑单 | 扭曲权重；且 `min_cash: 0.10` 本就要留现金 |
| 一次性建满仓位 | 全部成本基础由一天价格决定；污染归因 |
| 分批期间分数下跌就卖出已建仓部分 | 建仓计划不应自带止损逻辑，职责混乱 |
| 分数都低时推荐"相对最好的" | `min_score` 的设计本就允许空仓。买"相对最好的"是自欺 |
| 只发清单不发成绩 | 加剧 R-24；用户无法判断该不该信 |
| 用用户实际执行的部分做归因 | "只买了涨的那几只"让统计失真 |
| 自动探测用户板块权限 | A 股无 API，探测不到；只能声明式配置 |
| eligibility 默认全开 | 会推荐用户无权限交易的标的，清单不可执行 |
| 未开通板块直接从研究里也删掉 | 研究需覆盖全市场；只在推荐环节过滤 |
| 放在 P1/P2 做 | 缺相关性去冗余会推出一篮子高相关标的；且 MVP 禁止买卖建议 |

## 后果

**正面**：
- 无新增 Agent，无新增 LLM 成本（复用现有管道）
- 资金量约束让推荐真正可执行
- 分批建仓降低时点风险，也让归因更干净
- `recommendation` append-only 对抗选择性记忆
- 支持"暂不建仓"这个正确但反直觉的输出

**负面**：
- 分批建仓拉长建仓周期（4 批 × 5 日 ≈ 1 个月），期间市场可能已变
- 小资金用户能获得的持仓数少，分散度受限
- 整手取整在小资金下误差占比大
- 需维护第三种持仓状态，增加数据模型复杂度
- "暂不建仓"容易被用户当成系统没用

**必须接受的代价**：分批期间若市场快速上涨，后续批次成本更高。这是降低时点风险的对价——**不追求最优买点，追求避免最差买点**。

## 一个容易被误解的输出

`min_score: 0.55` 允许空仓。冷启动时会产生：

```
## 结论：暂不建仓

候选池中无标的达到入选门槛（min_score = 0.55）。
当前最高分：0.51（600xxx）
建议：保持现金。下次评估：2026-09-08
```

**这是一个正确答案，不是系统故障。** 但用户问"我该买什么"得到"什么都别买"，很容易被当成没用。所以文案必须给出最高分与门槛的距离、依据、下次评估时点——**让它成为一个有信息量的结论**。

## 复审条件

- 若推荐执行率持续 < 30%，说明推荐不可执行（资金/整手/涨停），调整参数或缩小适用资金区间
- 若分批建仓的后续批次频繁被 abort，检查 `min_score` 是否过于敏感
- 若 shadow 成绩长期不超过随机选股 95 分位，**应停止发布该功能**（而非继续发但小字标注）
- 若接入 API 后可自动执行，重新评估分批间隔（自动执行可以更细粒度分批）
- 科创板/北交所最小申报数量若与假设不符，需修正 `derive_top_n`

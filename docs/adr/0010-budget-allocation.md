# ADR-0010: 分项预算与调用前拦截

- 状态: 已接受
- 日期: 2026-08-31
- 相关: [16-token-economics](../16-token-economics.md), [14-risk-register](../14-risk-register.md) R-11

## 背景

LLM 成本不是"优化项"，而是决定系统能否长期运行的约束。一个每天花 $5 的系统，一年 $1800——对个人研究项目会直接导致停摆。

成本失控通常是渐进的：加一个 Agent、多分析几只股票、上下文变长一点，每一步看起来都合理。

需要决定两件事：
1. 预算怎么分配
2. 什么时候检查

## 决策

**分项预算 + 调用前估算拦截 + 分项独立降级。**

```yaml
budget:
  daily_usd_limit: 1.50
  allocations:
    daily_research: 0.80      # 盘后研究流程
    monitoring: 0.30          # 盘中监控
    news_extraction: 0.30     # 新闻事件抽取
    adhoc: 0.10               # 临时调用
  on_exceed:
    daily_research: "degrade"    # 减少 StockAgent 数量
    monitoring: "l1_only"        # 降为纯规则监控
    news_extraction: "skip"      # 跳过，次日补
    adhoc: "abort"
```

三条硬约束：

1. **调用前检查**：用 tokenizer 精确算输入，用 `max_tokens_out` 作输出上界，超限则抛异常或降级
2. **分项独立，互不挪用**：研究流程不能吃掉监控的预算
3. **降级必须在输出中显式声明**：不允许静默降级

## 理由

### 为什么调用前而非事后

**事后统计毫无用处——钱已经花了。**

常见的错误做法是记录成本、生成报告、月底发现超支。这时候唯一的选择是"下次注意"，而"下次"同样会超。

调用前拦截把预算从"目标"变成"约束"。

```python
# ❌ 事后：无法拦截
result = await llm.complete(prompt)
self._record_cost(result.usage)

# ✅ 事前：可以拦截
reservation = budget.check_and_reserve(allocation, est_in, est_out, tier)
result = await llm.complete(prompt)
reservation.settle(result.usage)
```

### 为什么分项独立

如果用单一总预算，会出现这个失败模式：

```
盘后研究流程（17:00）花掉 $1.40
        ↓
次日盘中监控（09:30）无预算可用
        ↓
监控失效 —— 而监控的价值密度更高
```

监控的单位价值更高：一条止损提醒可能避免 5% 的损失，而一份研究日报的边际价值低得多。所以监控预算必须受保护。

分项独立也让成本归因更清晰：能回答"研究流程和监控各花了多少"。

### 为什么降级而非中止

对多数分项，降级比中止好：

| 分项 | 降级后保留的能力 |
|---|---|
| `daily_research` | 板块分析仍在，只是不做个股 |
| `monitoring` | **止损、跌停、停牌、风控告警仍有效** |
| `news_extraction` | 新闻仍入库，只是不抽取结构化事件 |

只有 `adhoc`（临时研究调用）用 `abort`——因为它是可以稍后再跑的。

### 为什么降级必须声明

用户看到日报时，需要知道它是否完整。静默降级会让用户基于不完整的信息做决策，且不知道信息不完整。

```
今日报告说明：因预算限制未进行个股层面分析（降级）。
板块排序仍基于完整数据。
```

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 单一总预算 | 一个功能会吃掉其他功能的预算 |
| 事后统计成本 | 无法拦截，钱已花完 |
| 超预算后提高预算 | 预算是约束不是目标。这是自欺 |
| 按月预算而非按日 | 月初可能一次性花完，之后整月无预算 |
| 不设预算，靠优化控制 | 优化有上限，需求会增长。必须有硬顶 |
| 超限时静默降级 | 用户基于不完整信息决策而不知道 |
| 按 Agent 设预算 | 粒度过细，且新增 Agent 需改配置。按用途分更稳定 |

## 后果

**正面**：
- 成本有硬上限，不会失控
- 关键功能（监控）的预算受保护
- 成本归因清晰（可查各分项、各 Agent 的开销）
- 超限时系统仍能工作（降级而非崩溃）

**负面**：
- 需要为每次调用估算 token（有一定开销）
- 输出 token 只能估上界，可能过于保守（导致提前降级）
- 分项配置需要调优（初期分配可能不合理）
- 降级逻辑增加代码复杂度

**估算不准的处理**：输入 token 可精确计算；输出用 `max_tokens_out` 作上界。这会导致保守估计（实际输出通常少于上限），可能提前触发降级。可接受——保守优于超支。

## 配套的成本优化手段

预算是硬顶，但也需要主动优化。按投入产出比排序（详见 16 文档）：

| # | 手段 | 节省 |
|---|---|---|
| 1 | L1 规则前置过滤（监控） | ~99% |
| 2 | 量化粗筛替代 LLM 粗筛 | ~95% |
| 3 | Prompt 中不放数据，改用工具 | ~80% |
| 4 | 输出 schema 去掉 reasoning 字段 | ~70% 输出 |
| 5 | 只传标题摘要不传全文 | ~80% |
| 6 | 批处理 | ~40% |
| 7 | 模型分层 | ~60% |
| 8 | 工具返回值截断 | ~30% |

前 8 项都是低难度高收益，P2 一次做完。

## 质量指标

成本控制的目标不是"最省"，而是"每花的钱都有价值"。核心指标：

```sql
-- 每条有用推送的成本
SELECT sum(cost_usd) / count(*) FILTER (WHERE feedback = 'useful')
FROM alert WHERE created_at > now() - interval '30 days';
```

目标 < $0.30。若超过，说明系统在为无用推送买单，应削减噪声触发器而非提高预算。

## 复审条件

- 若实测成本远低于预算（< 50%），可考虑增加 StockAgent 数量提升覆盖
- 若某分项持续超限，需审查该分项的优化空间，而非直接提高分配
- 若单条有用推送成本 > $0.30，审查触发器质量
- 若引入按需付费之外的定价模式（如订阅制），重新评估预算机制

# ADR-0004: 自建回测引擎

- 状态: 已接受
- 日期: 2026-08-31
- 相关: [01-tech-stack](../01-tech-stack.md), [08-backtest-eval](../08-backtest-eval.md)

## 背景

需要一个日频截面选股的回测引擎。候选现成方案：backtrader、vectorbt、zipline、Qlib。

A 股有三条特殊规则必须准确模拟：

| 规则 | 影响 |
|---|---|
| T+1 | 当日买入不可卖出 |
| 涨跌停不可成交 | 涨停买不进、跌停卖不出 |
| 停牌 | 无法交易但需估值 |

第二条影响最大：动量策略最想买的往往正是涨停的股票。不模拟会系统性高估收益，幅度常超过滑点影响。

## 决策

**自建回测引擎。** 核心是 `SimulatedBroker`，从 P0 就实现，同时用于回测、Shadow Portfolio、单元测试。

关键设计：回测与实时**共享 Stage 3-5 代码**（因子 → 预测 → 融合 → 组合 → 风控），区别只在注入的数据源和 Broker 实现。

## 理由

**A 股规则必须是一等公民，不是补丁。** 通用框架的撮合逻辑是为美股设计的，加 A 股约束需要深度改造。改造后的框架比自建更难维护。

**我们的需求很窄**：
- 日频，不需要事件驱动的 tick 级引擎
- 截面选股，不需要复杂的订单类型
- 目标权重再平衡，不需要复杂的仓位管理

这个范围自建约 1000 行，完全可控。

**可审计性。** 回测结果的可信度是项目根基。自建意味着每一行撮合逻辑都能审查。用框架则要相信它的实现正确（而这些框架对 A 股规则的处理往往不正确）。

**与实时共享代码。** 这是防止"回测专用逻辑"这类 bug 的关键。框架通常有自己的数据格式和生命周期钩子，难以与实时流程共用。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| backtrader | 事件驱动设计对日频截面策略过重；社区活跃度下降 |
| vectorbt | 向量化很快，但对涨跌停/停牌/T+1 的处理需大量 hack，且 hack 后失去性能优势 |
| zipline | 已停止维护；美股假设深度耦合（交易日历、结算、订单类型） |
| Qlib | 功能强大且专门针对 A 股，但**框架侵入性强**——要按它的数据格式和工作流组织整个项目。与我们的 PIT 数据模型冲突 |
| 直接用 pandas 手写循环 | 这就是自建，只是没有抽象。我们要的是有结构的自建 |

### 关于 Qlib 的补充

Qlib 是最接近需求的选项，否决理由需要说明：

- 它要求数据按其 `.bin` 格式组织，与我们的 PIT PostgreSQL 模型冲突
- 它的 `D.features()` 接口不支持 `as_of` 语义
- 采用它意味着整个数据层要围绕它设计，而 PIT 是我们的第一优先级（ADR-0001）

**但会选择性借用**：Qlib 的因子表达式设计思路、部分评估指标实现可以参考。这是"参考"不是"依赖"。

## 后果

**正面**：
- A 股规则准确模拟
- 每行撮合逻辑可审查
- 与实时共享代码，杜绝"回测专用逻辑"
- `SimulatedBroker` 一份代码四处复用（回测/Shadow/测试/A股执行）
- 可注入故障用于测试异常路径

**负面**：
- 需自己实现撮合、成本、指标计算
- 无现成的可视化工具
- 需自己保证正确性（靠单因子测试交叉验证）

**正确性验证手段**：单因子回测结果必须与独立计算的 IC 分析一致。若不一致，说明回测引擎有 bug。这是 P1 的重要验收项。

## 复审条件

- 若需要 tick 级或事件驱动回测 → 重新评估
- 若自建代码超过 3000 行 → 说明需求已超出预期，重新评估
- 若出现难以自建的需求（如复杂期权定价）→ 局部引入专用库

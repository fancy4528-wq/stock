# ADR-0003: 不使用 LangChain 等 Agent 框架

- 状态: 已接受
- 日期: 2026-08-31
- 相关: [01-tech-stack](../01-tech-stack.md), [06-agent-design](../06-agent-design.md)

## 背景

系统需要多 Agent 编排：Chief → Sector → Stock，含并发控制、工具调用、结构化输出、追溯记录、成本控制。

现成方案有 LangChain、LangGraph、CrewAI、AutoGen 等。

## 决策

**自建薄编排层**，只依赖 LLM 官方 SDK + Pydantic。

核心只需三个组件：

```python
class LLMClient:      # 统一调用、重试、计量、缓存
class Agent[TOut]:    # 工具注册 + 结构化输出 + trace
class Orchestrator:   # 并发控制 + 依赖顺序 + 预算控制
```

## 理由

**我们的编排很简单。** Chief → Sector → Stock 是固定 DAG，不需要动态图执行引擎、循环、条件分支。用 `asyncio.gather` 加信号量就够了。

**追溯需求特殊。** 我们要把每次 LLM 调用关联到：数据版本（`as_of`）、evidence ID、run_id、token 成本。框架的 tracing 抽象不匹配这个需求，硬套会更麻烦。

**Token 成本必须精确可控。** 需要在调用前估算 token 并做预算检查。框架的自动 prompt 组装是黑盒，无法精确预估。

**抽象泄漏。** 出错时需要读框架源码才能理解发生了什么。对于一个人维护的项目，这是不可接受的调试成本。

**版本稳定性。** LangChain 的 API 有频繁破坏性变更的历史。锁死版本则无法获得修复。

**PIT 注入需求。** 我们要求框架在工具调用时强制注入 `as_of`，且 Agent 的 tool schema 里不能出现这个参数。这是自定义 dispatch 逻辑，框架不支持。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| LangChain | 抽象泄漏、版本不稳、我们的需求太简单用不上它的复杂度 |
| LangGraph | 图执行引擎对固定 DAG 是过度设计。若将来需要动态图可再引入 |
| CrewAI | 角色抽象与我们的设计不匹配（我们的 Agent 不"对话"，是流水线） |
| AutoGen | 侧重多 Agent 对话，我们不需要 Agent 间协商 |
| 完全不用结构化输出，靠解析文本 | 无法可靠消费、无法自动评估 |

## 后果

**正面**：
- 完全可控，出错能直接定位
- Trace 与追溯需求完美匹配
- Token 成本精确可控
- `as_of` 强制注入可实现
- 依赖少，升级风险低

**负面**：
- 需要自己写重试、并发、限流逻辑（但代码量不大）
- 无法直接使用框架生态的现成工具/集成
- 若将来编排复杂度大幅上升，需要重构

**代码量估算**：三个核心组件约 500-800 行。相比学习和调试框架的成本，这是划算的。

## 保留的退路

如果后期编排复杂度真的上升（需要动态图、循环、人工介入节点），可以引入 LangGraph。届时只需替换 `Orchestrator`，`Agent` 和 `LLMClient` 保持不变。

这是分层设计的好处：编排逻辑与 Agent 实现解耦。

## 复审条件

- 编排出现动态图需求（下一步取决于运行时结果）
- 需要 Agent 间多轮协商
- 需要人工介入节点（human-in-the-loop 工作流）
- 自建代码超过 2000 行（说明需求已超出"薄编排层"）

# ADR-0001: 采用 Point-in-Time 数据模型

- 状态: 已接受
- 日期: 2026-08-31
- 相关: [03-data-model](../03-data-model.md), [14-risk-register](../14-risk-register.md) R-01

## 背景

金融数据会被追溯修改：财报重述、行业分类调整、指数成分变更、复权因子随除权变化。

如果数据库只存"最新版本"，回测时查询到的就是当前值，而非决策时点真实可见的值。这构成未来函数，会让回测结果系统性虚高，且**不会产生任何报错**。

这是量化项目最常见也最致命的错误，症状是"回测漂亮、实盘失效"，事后极难诊断。

## 决策

所有可变数据采用双时间轴存储：

| 数据类型 | 策略 |
|---|---|
| 不可变（未复权日线） | 单版本，`trade_date` |
| 可修订（财报、复权因子、宏观） | `(key, revision)` + `announced_at` |
| 区间有效（行业归属、成分股、ST 状态） | `valid_from` / `valid_to` |

配套约束：

1. 所有历史数据查询必须走 `PITRepository`，`as_of` 为 keyword-only 且无默认值
2. PIT 逻辑封装为 PostgreSQL 函数（`get_financials_as_of` 等）
3. 禁止业务代码写 SQL（CI 静态检查）
4. 运行时 `assert_no_lookahead` 断言
5. **未来函数哨兵测试**：向未来注入荒谬数据，历史回测结果不应改变

## 理由

未来函数是唯一"会让整个项目失去意义"的技术错误。其他错误可以修，但基于泄漏数据得出的所有结论都要作废。

在 P0 就付出这个成本，比后期发现再重做全部回测便宜得多。

`as_of` 设为 keyword-only 无默认值是刻意的：忘记传会直接 `TypeError`，而不是静默使用默认值。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 只存最新值，回测时人工注意 | 人一定会忘。且无法验证是否忘了 |
| 存快照（每日全量复制） | 存储爆炸，且仍无法表达"这条数据何时可见" |
| 用数据源提供的 PIT 接口 | akshare/tushare 无此能力；付费源成本高 |
| 存复权后价格 | 前复权价随每次除权变化，等于历史数据被静默改写 |
| 事后加 PIT | 已有回测结果全部作废，成本远高 |

## 后果

**正面**：
- 回测结果可信
- 数据修订历史可查（能分析重述对策略的影响）
- 支持"如果当时知道 X 会怎样"的反事实分析

**负面**：
- 数据库设计复杂度上升（三种存储模式）
- 写入逻辑复杂（修订产生新 revision 而非 UPDATE）
- 存储量增加（保留全部修订版本）
- P0 工作量显著增加

**必须接受的代价**：P0 从"两周搭个数据库"变成"3-4 周建 PIT 数据层"。

**残余风险**：LLM 的训练数据可能包含"未来"信息（知识截止日之后的历史）。这无法通过数据层解决，只能靠 Agent 层的前向验证（Shadow Portfolio）。

## 复审条件

- 若发现某类数据的修订从不影响策略结论，可考虑简化其存储
- 若存储量成为瓶颈（预计不会，日线数据量极小）

# 14 — 风险登记册

## 1. 评级标准

| 概率 | 定义 |
|---|---|
| 高 | 大概率发生（> 60%） |
| 中 | 可能发生（20-60%） |
| 低 | 不太可能但需防范（< 20%） |

| 影响 | 定义 |
|---|---|
| 致命 | 项目失去意义或造成实际资金损失 |
| 严重 | 需大幅返工或结论不可信 |
| 中等 | 需局部返工或降低效果 |
| 轻微 | 可接受，有变通方案 |

## 2. 研究方法论风险（最危险的一类）

这类风险的共同特点：**不会报错，只会让你得到错误的信心。**

### R-01 未来函数泄漏

| 项 | 内容 |
|---|---|
| 概率 | **高** |
| 影响 | **致命** |
| 表现 | 回测年化 50%+，实盘立即亏损 |
| 为什么危险 | 无任何报错，且回测越漂亮越不会去怀疑 |

泄漏途径清单：

| # | 途径 | 防范 |
|---|---|---|
| 1 | 财务数据用 `period` 而非 `announced_at` 过滤 | SQL 函数强制 |
| 2 | 用当前行业分类回溯历史 | 区间表 |
| 3 | 用当前指数成分回溯 | `universe_snapshot` |
| 4 | 复权因子未 PIT（除权后历史价被改写） | 存未复权价 + 因子版本 |
| 5 | 标签用 T 日收盘价（决策日当天） | 标签用 T+1 开盘价 |
| 6 | 模型训练期与预测期重叠 | `validate_prediction` |
| 7 | Walk-forward 无 embargo，标签跨界 | embargo ≥ 预测期 |
| 8 | RAG 检索到未来新闻 | `visible_at <= as_of` |
| 9 | Agent 引用未来 evidence | `check_evidence_pit` |
| 10 | 宏观数据用 `period` 而非发布时间 | `macro_observation.announced_at` |
| 11 | 截面标准化用了全期统计量 | 只用当期截面 |
| 12 | 异常值处理用了全样本分位 | 滚动窗口 |
| 13 | LLM 训练数据含"未来"（知识截止日之后的历史） | Agent 层只做前向验证 |
| 14 | 年报 chunk 用报告期末而非披露日 | `document_chunk.visible_at` 校验 |
| 15 | 检索到当时尚未生效的规则文档 | `expires_at` 双向过滤 |
| 16 | thesis chunk 用 `as_of_date`（片段含结果） | `visible_at` = 结果确认时间 |
| 17 | K4 归因结论被更早的回测检索到 | `visible_at` = 归因完成时间 |

第 16、17 条是知识层特有的，也最隐蔽——**用后来总结的规律去回测过去**，是过拟合最常见的伪装形式。见 [17-knowledge-base](17-knowledge-base.md) 4.3 / 5.2 节。

缓解措施：
- PIT 数据模型（03 文档）
- `as_of` keyword-only 强制传参
- 运行时 `assert_no_lookahead`
- **未来函数哨兵测试**（最有效，P0 就实现）
- CI 静态检查禁止业务代码写 SQL

**残余风险**：第 13 项无法完全解决。LLM 可能"记得"历史结果。这是 Agent 层必须靠 Shadow Portfolio 前向验证的根本原因。

### R-02 过拟合

| 项 | 内容 |
|---|---|
| 概率 | **高** |
| 影响 | **严重** |
| 表现 | 每次调参回测都更好，实盘失效 |
| 为什么危险 | 过程感觉像"改进"，实际在消耗样本外有效性 |

缓解：

| 措施 | 说明 |
|---|---|
| `param_search_count` 记录 | 累计次数写入 `backtest_run`，两位数时警告 |
| 封存期 + `HoldoutGuard` | 只能用一次，第二次抛异常 |
| 限制超参搜索空间 | LightGBM 只调 5-6 个参数 |
| 强制模型演进顺序 | L4 必须优于 L2 才采用 |
| 多轮 walk-forward 一致性 | 各轮差异大 = 不稳定 |
| 参数敏感性检查 | 微调导致剧变 = 过拟合 |
| 特征重要性稳定性 | 每轮重要特征应大致一致 |
| 蒙特卡洛随机选股对照 | 结果需超出随机 95 分位 |

**残余风险**：中。过拟合无法完全避免，只能限制程度并保持警惕。

### R-03 生存者偏差

| 项 | 内容 |
|---|---|
| 概率 | 中 |
| 影响 | 严重 |
| 表现 | 回测收益虚高，尤其小市值策略 |

缓解：退市股票保留（`delist_date`）、`universe_snapshot` 按时点、退市损失计入、自动检查"池中是否含后来退市的股票"。

### R-04 涨跌停成交假设错误（A 股特有）

| 项 | 内容 |
|---|---|
| 概率 | **高** |
| 影响 | **严重** |
| 表现 | 动量策略回测优异，实盘买不进 |

这是 A 股回测最容易忽略且影响最大的问题。策略最想买的往往正是涨停的股票。

缓解：`is_limit_up/down` 字段、`SimulatedBroker` 强制检查、标签构造排除涨停样本、回测报告输出拒单统计。

**残余风险 —— 假设本身未被验证**：上述缓解措施全部是"让代码符合我的假设"，而**假设是否符合现实从未被检验**。`SimulatedBroker` 里有一批推断：涨停不可买入、成交量上限取值、集合竞价优先级、部分成交处理。单元测试只能证明代码符合假设，不能证明假设正确。

而**回测与 Shadow Portfolio 的全部结论都建立在这些假设上**。

唯一解法是拿真实撮合结果对比（券商模拟环境），见 [ADR-0012](adr/0012-cn-simulated-trading.md)。这是 Gate 7b 的硬条件，且**越早做越好**——若假设有错需重跑历史回测，越晚发现作废的越多。

### R-04a 撮合假设校准发现严重偏差

| 项 | 内容 |
|---|---|
| 概率 | 中 |
| 影响 | **严重** |
| 表现 | 校准发现某项假设完全错误，修正后历史回测结论翻转 |

这是 R-04 残余风险成真的情形。后果是回测层面的努力白费。

处理：**不是缓解，而是接受并尽早暴露。** 已写入 [12-roadmap](12-roadmap.md) 第 6 节退出条件——"回到 P4 重新评估，此前全部结论作废"。

**注意校准不设通过门槛**：目的是知道偏差多大，不是让它变小。设门槛然后调参数去满足，等于把校准变成另一种过拟合。

### R-05 信号相关性导致的隐性权重放大

| 项 | 内容 |
|---|---|
| 概率 | 高 |
| 影响 | 中等 |
| 表现 | 名义等权，实际某类信号占主导 |

Fusion 的 5 个信号中，quant / sector / stock 都含价格动量成分，等权相加可能实际给动量 50%+ 权重。

缓解：`components` 落库、P4 计算相关矩阵、相关性 > 0.7 的合并、按独立贡献重新加权。

### R-06 Agent 事后合理化

| 项 | 内容 |
|---|---|
| 概率 | **高** |
| 影响 | 中等 |
| 表现 | 报告写得很有道理，但无预测力 |

LLM 读新闻后给出的分析可能只是复述已被市场消化的信息。

缓解：`shadow_agent` 独立组合、Agent 输出 IC 检验、confidence 校准检验。

**必须接受的可能结论**：Agent IC ≈ 0。正确应对是降权并保留解释用途，而非反复调 prompt 直到 IC 变正（那是过拟合）。

## 3. 数据风险

### R-07 akshare 接口失效

| 项 | 内容 |
|---|---|
| 概率 | **高**（几乎必然，只是时间问题） |
| 影响 | 中等 |
| 表现 | 某天流程中断，或更糟：返回格式变化但未报错 |

缓解：双源架构、schema 校验、每日接口健康检查、锁定版本、`data-access-log.md` 记录、降级策略（宁可无输出不用错数据）。

### R-08 数据源单源错误未被发现

| 项 | 内容 |
|---|---|
| 概率 | 中 |
| 影响 | 严重 |

**残余风险**：资金流、概念板块等单源数据无法交叉校验，只能做内部一致性检查。

### R-09 tushare 积分不足

缓解：P0 阶段确认积分等级覆盖的接口清单、降级用 akshare 财务数据并标记质量、必要时考虑付费。

### R-10 历史数据无法回补

|---|---|

## 4. 成本风险

### R-11 LLM 成本超预算

| 项 | 内容 |
|---|---|
| 概率 | **高** |
| 影响 | 严重（可能导致项目停摆） |
| 表现 | 月账单远超预期，被迫关停功能 |

成本失控通常是渐进的：加一个 Agent、多分析几只股票、上下文变长一点，每一步看起来都合理。

缓解（详见 [16-token-economics](16-token-economics.md)）：

| 措施 | 节省幅度 |
|---|---|
| L1 规则前置过滤（监控） | ~99% |
| 量化粗筛替代 LLM 粗筛 | ~95% |
| Prompt 中不放数据，改用工具 | ~80% |
| 只传标题摘要不传全文 | ~80% |
| 输出 schema 去掉 reasoning | ~70% 输出 |
| 模型分层 | ~60% |
| 批处理 | ~40% |
| Prompt 前缀缓存 | ~30-50% 输入 |
| **分项预算 + 调用前拦截** | 上限保障 |

**关键机制：预算是硬约束，超限降级或中止，不是"下次注意"。** 事后统计毫无用处——钱已经花了。

### R-25 监控层成本失控

| 项 | 内容 |
|---|---|
| 概率 | 中 |
| 影响 | 中等 |
| 表现 | 新闻量激增（如市场剧烈波动时）导致成本飙升 |

盘中监控的处理量随市场情绪波动。极端行情下新闻量可能是平时的 5-10 倍。

缓解：
- L1 通过率监控（异常升高时告警，可能是关键词表问题）
- 监控专用预算独立，不挤占研究预算
- 预算耗尽降级为 L1（关键告警仍工作）
- L3 调用次数硬上限（每日 ≤10 次）

### R-26 三级漏斗过滤不足

| 项 | 内容 |
|---|---|
| 概率 | 中 |
| 影响 | 中等 |
| 表现 | L1 通过率过高（> 10%），L2 成本超预期 |

原因可能是：实体别名词典过于宽泛、关键词表包含高频词、持仓过于分散导致匹配面广。

缓解：Gate 2b 要求 L1 通过率 < 5%；持续监控通过率；定期审查关键词表。

## 5. 监控与推送风险

### R-27 推送疲劳

| 项 | 内容 |
|---|---|
| 概率 | **高** |
| 影响 | 严重（用户关掉通知，功能失效） |
| 表现 | 每天十几条推送，用户开始忽略 |

**这是监控功能最可能的失败方式。** 推送太多等于没有推送。

缓解：
- 每日推送硬上限（默认 10 条，critical 5 条）
- 冷却期（同一触发器同一标的 4-72 小时）
- medium 级汇总推送（11:30 / 14:45 两次）
- 静默时段（22:00-08:00，critical 除外）
- **反馈驱动淘汰**：有用率 < 20% 的触发器考虑关闭
- Gate 2a 要求日均 2-8 条（过少无用，过多疲劳）

### R-28 关键事件漏报

| 项 | 内容 |
|---|---|
| 概率 | 中 |
| 影响 | 严重 |
| 表现 | 持仓股立案调查，系统未推送 |

漏报比误报危险得多。

缓解：
- A/B/C 类触发器完全零 LLM（不受预算影响）
- 公告类型白名单人工维护并定期审查
- Gate 2a 要求连续 20 交易日无漏报（人工抽检关键事件）
- 预算耗尽时降级为 L1，关键监控仍工作
- 实体别名词典定期从新闻中挖掘补充

### R-29 持仓数据陈旧

| 项 | 内容 |
|---|---|
| 概率 | **高** |
| 影响 | 中等 |
| 表现 | 用户已卖出但系统仍在监控，或已买入但未监控 |

A 股阶段持仓手工维护，必然会忘记更新。

缓解：
- 每日推送中显示"持仓数据更新于 X 天前"
- 超过 5 个交易日未更新则主动提醒
- 重要推送前校验持仓时效性
- 提供多种便捷录入方式（CLI / Telegram Bot / 对账单导入）
- 美股阶段从 API 自动获取（这是接 API 的实际收益之一）

### R-30 推送投递失败

| 项 | 内容 |
|---|---|
| 概率 | 中 |
| 影响 | 中等 |
| 表现 | 网络问题导致 critical 告警未送达 |

缓解：多渠道配置、投递失败重试、`alert.delivery_error` 记录、Gate 2a 要求投递成功率 > 99%。

### R-31 监控被误当作自动交易

| 项 | 内容 |
|---|---|
| 概率 | 低 |
| 影响 | 中等 |
| 表现 | 用户以为系统会自动执行止损 |

缓解：推送文案明确"建议"而非"已执行"；文档明确监控不触发交易；A 股阶段本就无 API。

### R-32 知识库注入系统性偏见

| 项 | 内容 |
|---|---|
| 概率 | 中（若不加约束则为高） |
| 影响 | 严重 |
| 表现 | Agent 观点看似独立，实为知识库作者的先验 |

若知识库含投资流派材料（价值/动量/成长），Agent 会在所有标的上寻找符合该流派的理由。这个结论不来自当期数据，但 Fusion 层会当作独立观点采纳。

**这是一种比 R-05 更隐蔽的信号相关性** —— 它藏在 prompt 里而不在数据里，用相关性矩阵查不出来。

缓解：
- 知识库明确不放投资流派与方法论材料（[ADR-0011](adr/0011-no-general-finance-kb.md)）
- 通用金融概念不注入（预训练已掌握）
- 制度规则走配置，规则参与计算不参与推理
- Agent 输出的每个论点须有 `evidence_ids`（`check_evidence_pit`）

### R-33 历史 thesis 检索产生锚定

| 项 | 内容 |
|---|---|
| 概率 | 中 |
| 影响 | 中等 |
| 表现 | Agent 看到"三个月前我看多"，倾向维持看多以保持一致 |

这是人的偏误，LLM 同样有。表现为结论一致性上升但准确率没变——看起来更"稳定"，实际是停止思考。

缓解：
- Prompt 明确"结论必须基于当期数据独立得出，冲突时以当期为准"
- P4 做 A/B 测试：有无历史检索的准确率对比
- 同时监控结论多样性，若显著下降而准确率未升，关闭该功能
- `top_k` 默认 3（少量相关的比大量泛泛的有用）

### R-34 K4 经验库膨胀失效

| 项 | 内容 |
|---|---|
| 概率 | 中 |
| 影响 | 轻微 |
| 表现 | 人工维护的"经验"累积成一堆无用感想，检索命中率下降 |

缓解：三条硬准入标准（可验证 / 可操作 / 有时效）+ 50 条硬上限 + `expires_at` 定期清理。

## 7. 技术风险

### R-13 状态不一致（实盘）

| 项 | 内容 |
|---|---|
| 概率 | 中 |
| 影响 | **致命**（可能造成资金损失） |
| 表现 | 本地以为持仓 1000 股，实际 500 股 |

缓解：每日多次对账、券商为唯一真相来源、不一致触发 kill switch、幂等下单、状态机校验、20 项异常路径测试。

### R-14 重复下单

| 项 | 内容 |
|---|---|
| 概率 | 中 |
| 影响 | **致命** |
| 表现 | 网络超时后重试，实际下了两笔 |

缓解：
- `client_order_id` 确定性生成（重跑得到相同 ID）

- Redis 短期锁防并发

- 故障注入测试

### R-15 Kill Switch 失效

| 项 | 内容 |
|---|---|
| 概率 | 低 |
| 影响 | **致命** |

缓解：独立于 RiskEngine 实现、Redis 存储（进程重启不丢）、每次下单前检查、恢复需确认串、定期演练。

### R-16 QMT 部署环境不兼容

| 项 | 内容 |
|---|---|
| 概率 | 中 |
| 影响 | 中等 |

缓解：`QMTAdapter` 作为独立服务 + HTTP/gRPC 调用、抽象层设计不受影响。这个风险到 P7b-1 才需要解决。

### R-35 QMTAdapter 首次上线即接实盘

| 项 | 内容 |
|---|---|
| 概率 | 中（若不拆阶段则为高） |
| 影响 | **严重** |
| 表现 | 工程风险最高的组件在最高风险的环境里首次运行 |

`QMTAdapter` 是全项目工程风险最高的组件：Windows 进程约束、IPC 通信、公开文档少、xtquant 行为需自行摸索。

原路线的不对称：

```
P7a 美股  前置: Gate 6 + Paper 连续 1 个月    ✅
P7b A股   前置: 权限 + 合规报告                ❌ 无模拟要求
```

**方向错了** —— A 股规则更复杂（T+1、涨跌停、多板块不同幅度、ST），技术栈风险也更高，准入应更严不是更松。

缓解（[ADR-0012](adr/0012-cn-simulated-trading.md)）：
- P7b 拆为 P7b-1（模拟环境验证）+ P7b-2（实盘）
- 新增 Gate 7b，与 Gate 6 对称
- 20 项异常路径必须在**真实 API** 上验证（非 mock）
- 模拟环境连续运行 ≥ 1 个月
- ~~若模拟环境门槛低于实盘权限，P7b-1 可与 P2-P6 并行~~ **已核实推翻**：模拟盘 API 与实盘 API 同一套权限，无法提前并行，见 R-44

### R-44 A 股自动化链路无法提前端到端验证

| 项 | 内容 |
|---|---|
| 概率 | **高**（已确认为事实约束） |
| 影响 | 严重 |
| 表现 | 拿到券商量化权限（最低 5 万 + 6个月经验 + C4/C5）前，连模拟盘 API 都调不了，`QMTAdapter` 与撮合校准无法验证 |

2026-09-03 核实（[00-overview](00-overview.md) 7.1a）确认：**API 调用模拟盘与调用实盘用同一套量化接口权限**。原以为"模拟门槛低可提前并行验证"不成立。这使全项目工程风险最高的组件被迫压到关键路径末端，且验证时间取决于开发者自身何时达到券商门槛（资金 + 经验），时间不可控。

缓解：
- `QMTAdapter` 的接口抽象、撮合假设、单元测试提前写（不依赖真实连接）
- **用美股 Alpaca Paper 通道先跑通端到端自动化链路**（注册即用、有沙盒），验证 Proposal → Risk → Execution 的代码路径，A 股权限达成时接的是"已验证框架 + 新 Adapter"
- 权限达成前 A 股走「研究 + 人工执行清单」（[09-portfolio-risk](09-portfolio-risk.md) 第 6 节），先验证研究质量
- 在 00-overview 明确记录：A 股 API 接入依赖开发者自身达到券商门槛，时间不确定

### R-45 未完成程序化交易报告即接实盘（合规违规）

| 项 | 内容 |
|---|---|
| 概率 | 中（若不设前置检查则为高） |
| 影响 | **严重**（合规违规，可能被收回权限） |
| 表现 | A 股接实盘 API 自动下单，但未先完成"程序化交易报告"，违反"先报告、后交易" |

2023 年起程序化交易报告制度要求：只要是程序自动下单，无论资金/频率，都须在交易前报告并经接收确认（[00-overview](00-overview.md) 5.2a）。本系统一旦接 A 股实盘即触发。

缓解：
- **P7b-2 实盘的合规前置**：报告完成并确认前，A 股实盘开关无法打开
- 实盘开关的"显式确认"（六条原则第 4 条）加一项勾选："已完成程序化交易报告并获接收确认"
- 系统能导出报告所需信息（策略类型、执行方式、申报速率上限、软件版本）
- 策略/申报速率发生重大变更时提示重新变更报告（下一自然月前 5 个交易日内）
- 本系统日频、MiniQMT，申报速率远低于高频阈值（300 笔/秒、20000 笔/日），不触发高频额外报告

### R-36 免费模拟炒股制造虚假信心

| 项 | 内容 |
|---|---|
| 概率 | 低（已明确排除） |
| 影响 | 中等 |
| 表现 | 用同花顺/东财模拟盘"验证"策略，撮合过松导致高估可行性 |

免费模拟炒股多数报价即成交、不排队、无滑点，会让人以为涨停能买进、大单没有冲击成本。且它无 API，验证不了程序化链路——而这恰恰是唯一需要验证的东西。

这与 R-24（误当赚钱工具）同向叠加。

缓解：文档明确排除（[ADR-0012](adr/0012-cn-simulated-trading.md)、[10-execution](10-execution.md) 3.0 节的三种"模拟盘"辨析）。

## 9. 认知风险（最容易被忽略）

### R-21 建议模式的自欺

| 项 | 内容 |
|---|---|
| 概率 | **高** |
| 影响 | 严重 |
| 表现 | 只记住系统对的时候，忽略错的时候 |

A 股阶段只给建议不下单，缺少真实反馈约束。人会不自觉地选择性记忆。

缓解：
- **Shadow Portfolio 自动记录、append-only 触发器**
- 未执行项也要记录（涨停买不进是真实的机会损失）
- 月度自评报告强制展示全部数据
- 决策日志不可事后修改

这个风险的缓解措施是纯工程手段——**让数据无法被篡改**，比依靠自律可靠。

冷启动推荐会放大这个风险：用户会记住"推荐的那只涨了"，忘记"我没买"和"另外 11 只没涨"。额外缓解见 R-39。

### R-37 一次性建仓的时点风险

| 项 | 内容 |
|---|---|
| 概率 | **高** |
| 影响 | 中等 |
| 表现 | 12 个持仓一天买完，成本基础由一天价格决定 |

调仓每天只动边际，冷启动一次性决定**全部**仓位。若那天恰好是局部高点，之后很长时间在解套。

更麻烦的是它污染归因：**无法区分"策略不行"和"建仓时点不好"。**

缓解：
- 分批建仓**默认开启**（4 批 × 5 交易日间隔）
- 首批 40%，避免拖太久
- 分批期间中止条件（分数跌破门槛 / 触发排除规则 / 组合回撤超阈值）
- 中止只停止后续加仓，**不卖出已建仓部分**（卖出走正常调仓与风控）
- **分批追加只在 `investable` 内**，stance 转好由系统推送 `REC_STANCE_UP`，绝不自动动用未投入资金

**必须接受的代价**：分批期间市场快速上涨时后续批次成本更高。这是对价——不追求最优买点，追求避免最差买点。

### R-38 小资金无法执行推荐

| 项 | 内容 |
|---|---|
| 概率 | **高** |
| 影响 | 中等 |
| 表现 | 推荐 15 只，用户资金只够买 5 只，清单大部分不可执行 |

A 股买入最小 100 股（科创板 200 股，**需核实**）。资金 5 万时买一手 100 元的股票就是 20% 权重——会被 RiskEngine 拒掉。

| 资金 | 单票上限 10% | 可买最高股价 | 可行持仓数 |
|---|---|---|---|
| 5 万 | 5,000 | 50 元/股 | 8-10 |
| 10 万 | 10,000 | 100 元/股 | 12-15 |

缓解：
- `top_n` 由资金量推导，不是常量
- 组合层新增可执行性排除规则（`last_price × min_lot_buy > capital × max_single_weight`）
- 被排除的标的**必须在输出中展示**（否则用户不知道错过了什么，也不知道加资金的价值）
- 资金 < 3 万时持仓数 ≤5（再分散每票买不到一手，且佣金最低 5 元吃掉收益）
- 整手向下取整，残差保留为现金，取整后重新过 RiskEngine
- **用户只投一部分时用可投入资金重算，不按总额打折**（打折会让标的达不到一手）

### R-39 推荐执行率低导致归因失真

| 项 | 内容 |
|---|---|
| 概率 | **高** |
| 影响 | 严重 |
| 表现 | 用户只买了后来涨的那几只，统计上系统"很准" |

这是 R-21 在冷启动场景的具体形态，且更隐蔽——因为看起来有真实持仓数据支撑。

缓解：
- **归因必须用 shadow portfolio，不用用户实际执行的部分**（代码审查 + 视图注释）
- `recommendation` 表 append-only 触发器
- `recommendation_execution` 记录实际执行与未执行原因
- `v_recommendation_quality` 强制展示执行率与**全部**推荐的结果分布
- 执行率持续 < 30% 触发退出条件（说明推荐不可执行，需调参数）

### R-41 推荐了用户无权限交易的板块

| 项 | 内容 |
|---|---|
| 概率 | **高** |
| 影响 | 中等 |
| 表现 | 给未开通科创板的用户推荐科创板股票，清单完全无法执行 |

比 R-38 更彻底：R-38 是"买不满一手"，R-41 是"一股都下不了单"。科创板/北交所需 50 万 + 24 个月经验 + C4，创业板需 10 万 + 24 个月 + C4（**已核实 2026-09-03，见 [05-market-config](05-market-config.md) 2.3**）。系统 A 股阶段无 API，无法自动探知用户权限。

缓解：
- 用户声明式配置 `eligibility_cn.yaml`，**默认最保守（仅主板）**
- `board not in tradable_boards` 进入 `EXCLUSION_RULES`（组合层排除）
- **研究分析保留全部板块，仅建仓推荐过滤**（同一分数，不同过滤器）
- 被排除标的按 `BOARD_NOT_ELIGIBLE` 展示，提示门槛与"开通后可解锁"
- `recommendation.tradable_boards` 记录，保证推荐可复现

### R-42 止盈止损配置误设或形同虚设

| 项 | 内容 |
|---|---|
| 概率 | 中 |
| 影响 | 中等 |
| 表现 | 用户把止损设成 -80%（等于没止损）或频繁触发的 -1%；或关闭后个股无限下跌 |

止盈止损阈值开放给用户自定义带来灵活性，也带来误设风险。

缓解：
- 系统对用户阈值做**边界校验**（`bounds`: 止损限定在 -3% ~ -30%），越界拒绝配置并提示，不静默纠正
- `DD_005`（个股浮亏 -25% 强制减仓）作为**用户配置无法突破的系统兜底地板**
- `exit_signal.user_action` 记录用户是否遵守自己的纪律，用于复盘
- 触发时快照 `policy_snapshot`，避免事后改阈值导致无法复盘

### R-43 系统助推顺周期加码

| 项 | 内容 |
|---|---|
| 概率 | 中 |
| 影响 | **致命**（资金损失，R-24 的放大） |
| 表现 | 系统在"形势好"（实为估值高位）时建议用户提高投入，助推追高 |

投入额调整建议（09 文档第 11 节）若做成"形势好就推可加码"，会系统性放大用户的顺周期行为——散户亏损很大一部分正是"行情好时加仓、回调时割肉"。"建议多投本金"是全系统比荐股更敏感的动作。

缓解（详见 [ADR-0015](adr/0015-investable-adjustment.md)）：
- **主动推送默认关闭**，需用户像开实盘一样显式开启
- 被动响应（用户主动问）默认可用，但输出**反面信息前置**
- 开启主动推送后强制**双向**（加码/减码都触发），避免单向助推
- 触发基于**机会质量**（高分且便宜的标的占比），**不含近期涨幅**
- **绝不给具体投入金额**——系统不知道用户整体财务状况
- 输出强制含估值分位、距高点、历史信号后 60 日表现分布（含亏损）
- 复审：开启用户若加码后亏损比例显著高于未加码时段，关闭功能

### R-40 冷启动推荐被当作荐股

| 项 | 内容 |
|---|---|
| 概率 | **高** |
| 影响 | **致命**（R-24 的放大） |
| 表现 | "给空仓用户的 12 只建仓清单"在观感上等同投资建议 |

日报是研究，建仓清单不是。这是整个系统里**最接近荐股**的功能。

**免责声明不够**，需要设计上的约束：

| 强制要求 | 作用 |
|---|---|
| 展示对照组（含随机选股 95 分位） | 让用户看到是否真的超出随机 |
| 展示 shadow 实际历史成绩（非回测数字） | 真实前向记录 |
| 展示过往推荐的结果分布（不只是好的） | 对抗选择性记忆 |
| 随机选股分位超过本策略时**显著标注** | 诚实优先于好看 |

目标：让用户看到的不是一份清单，而是**一份带成绩记录的清单**。

**若做不到（shadow 数据不足），该功能应延后而非降低要求。** 若 shadow 成绩长期不超过随机选股 95 分位，应**停止发布该功能**，而非继续发但小字标注。
